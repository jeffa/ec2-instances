# EC2 AMI discovery and lifecycle guide

The current Terraform configuration uses hardcoded AMI IDs. Those IDs are regional, architecture-specific, and eventually become stale. AMI discovery replaces fixed IDs with a rule that asks AWS for an image matching defined criteria.

The goal is not simply to use the newest image. The goal is to choose an image deliberately for each environment:

| Environment | Recommended image strategy |
|---|---|
| Disposable development lab | Discover the latest compatible image |
| Integration testing | Pin a known image, or promote a newly tested image |
| Production | Use an approved image pipeline and explicit promotion |

## What AMI discovery does

Terraform can query AWS for an AMI based on criteria such as:

- publisher/owner
- image-name pattern
- operating-system release
- CPU architecture
- virtualization type
- root-device type
- available state
- newest matching publication date

Terraform then supplies the discovered AMI ID to `aws_instance`. The code no longer needs a manually copied `ami-...` value for every region.

## Option 1: AWS Systems Manager public parameters

AWS publishes Systems Manager parameters for current Amazon Linux AMIs. The parameter value is an AMI ID for the configured AWS region.

Example:

```hcl
data "aws_ssm_parameter" "amazon_linux" {
  name = "/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64"
}

module "server" {
  # ...
  ami = data.aws_ssm_parameter.amazon_linux.value
}
```

The parameter path is regional even though the public parameter name is consistent. Choose the image variant deliberately, including architecture and kernel choice. AWS documents the available Amazon Linux public parameters and the `resolve:ssm:` launch syntax in [Reference the latest AMIs using Systems Manager public parameters](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/finding-an-ami-parameter-store.html).

This is the simplest option for Amazon Linux because AWS owns and maintains the image catalog.

## Option 2: Terraform `aws_ami` discovery

For Ubuntu, Debian, Red Hat, and SUSE, Terraform can query public AMIs using strict filters:

```hcl
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["official-publisher-id"]

  filter {
    name   = "name"
    values = ["official-image-name-pattern-*"]
  }

  filter {
    name   = "architecture"
    values = ["x86_64"]
  }

  filter {
    name   = "virtualization-type"
    values = ["hvm"]
  }

  filter {
    name   = "state"
    values = ["available"]
  }
}
```

Then use:

```hcl
ami = data.aws_ami.ubuntu.id
```

The publisher owner ID and image-name pattern must be confirmed for each distribution. Do not use a broad wildcard without an owner restriction; unrelated public images may match it.

The `aws_ami` data source supports `owners`, filters, and `most_recent`. Terraform fails when the query returns zero or multiple matches, which helps expose an incorrect or ambiguous query instead of launching an arbitrary image. See the [Terraform `aws_ami` data source documentation](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/data-sources/ami).

## Option 3: Curated AMI catalog

For integration environments, a curated catalog provides more control:

```hcl
variable "ami_catalog" {
  type = map(map(string))

  default = {
    us-east-1 = {
      ubuntu = "ami-..."
      debian = "ami-..."
    }
  }
}
```

The catalog can be maintained manually or generated by CI after an image has been tested. This approach requires occasional updates, but it prevents a newly published image from changing an integration environment unexpectedly.

A useful compromise is to support both modes:

```hcl
variable "ami_mode" {
  type    = string
  default = "latest"

  validation {
    condition     = contains(["latest", "pinned"], var.ami_mode)
    error_message = "ami_mode must be latest or pinned."
  }
}
```

Development uses discovery; integration uses the pinned catalog.

## Architecture must match the instance type

The current lab uses `t2.micro`, which is an x86_64 instance type. The AMI query must therefore select an x86_64 image.

If the lab later moves to an ARM-based instance type such as a Graviton family, the image must be ARM64 and application packages must support that architecture. Architecture should be treated as part of the AMI selection criteria, not as an afterthought.

## What happens when the latest AMI changes

Terraform compares the AMI used by the existing instance with the AMI returned by discovery. If the value changes, Terraform will normally replace the EC2 instance.

That behavior is desirable for a disposable lab, because the instance should be rebuilt from a current image. It is more consequential for persistent environments, where the image should be promoted through testing rather than changed automatically.

Always inspect the plan after changing AMI logic. A newly discovered image should appear as an intentional replacement, not as an unexpected side effect of an unrelated edit.

## Recommended design for this laboratory

The current data-driven server matrix should retain the distribution metadata but replace fixed AMI values with a discovery or catalog reference:

```text
server matrix
  ├── username
  ├── instance name
  ├── architecture
  ├── discovery rule or SSM parameter
  └── optional pinned AMI by region
```

Recommended defaults:

- Amazon Linux: AWS Systems Manager public parameter.
- Ubuntu/Debian/Red Hat/SUSE: strict `aws_ami` queries or a curated catalog.
- Development: latest compatible image.
- Integration: pinned, previously tested image.
- Current `t2.micro`: x86_64 images only.
- Every image query: exact owner, release, architecture, virtualization, and state filters.

## Implementation sequence

Implement this as a separate change from the completed six-slice refactor:

1. Upgrade and lock the AWS provider in a controlled change.
2. Confirm the target image publisher and naming pattern for each distribution.
3. Add data sources or SSM parameters without changing the server matrix shape.
4. Run `terraform plan` and record which instances would be replaced.
5. Test one distribution first, then two or three, then the full matrix.
6. Confirm the discovered image’s default username and package-manager behavior.
7. Add a pinned catalog or image mode for integration environments.
8. Document the image review and promotion process.

The current provider is pinned to the old AWS provider 3.x line. Provider modernization should happen before or alongside this work, but it deserves its own plan and test because provider upgrades can change resource behavior.

## Operational checklist

Before accepting an automatically discovered AMI:

- [ ] The owner/publisher is verified.
- [ ] The operating-system release is correct.
- [ ] The architecture matches the instance type.
- [ ] The image is available in the selected region.
- [ ] The expected default login user works.
- [ ] The SSH bootstrap succeeds.
- [ ] The Ansible Docker playbook succeeds.
- [ ] Required package repositories are reachable.
- [ ] The image does not unexpectedly require a different security-group or network setup.
- [ ] The Terraform plan shows only intended replacements.

## Summary

AMI discovery can remove the need to manually update image IDs, but it does not remove the need to test image changes. Use automatic discovery for disposable development, pin tested images for integration, and promote image versions deliberately for anything persistent.
